# I remember you! — заметки для разработчика

Документ по сопровождению аддона **IRememberYou**. Здесь описано, как аддон
устроен, какие инварианты нельзя нарушать при правках и что проверить перед
релизом.

Документация для пользователей лежит в `README.md` (английский) и
`README.ru.md` (русский). Этот файл — для того, кто будет менять код следующим.

---

## 1. Задача и жёсткие правила

Аддон отвечает на один вопрос: *«кто это, даже если игрок сменил аккаунт или
персонажа?»* Всё остальное существует, чтобы этому служить.

Правила, на которых держится дизайн. Не ломайте их без необходимости:

* **Никогда не считать убийства.** Kill feed читается только как источник имён.
* **Никогда не писать в чат другим игрокам.** Всё выводится через
  `IRY:Print` → `CHAT_ROUTER:AddSystemMessage`, то есть только локально.
* **Никакого импорта/экспорта.** У аддонов ESO нет доступа к файлам. База — это
  SavedVariable `IRememberYouSV`, общая на весь аккаунт.
* **Срок хранения по умолчанию 0 (не забывать никогда).** Удаление данных —
  всегда явное действие пользователя.
* **Стилизуется только рамка цели под прицелом.** Рамки группы, неймплейты и
  все прочие юнит-фреймы остаются с именами от игры (решение «вариант 2»).
* **Пути отрисовки не меняют хранилище.** Показать имя можно, научиться чему-то
  из отрисовки — нельзя.

## 3. Жизненный цикл

```
EVENT_ADD_ON_LOADED (имя аддона совпало)
  ZO_SavedVars:NewAccountWide(svName, schema, nil, IRY.BuildDefaults())
  IRY.Store:Initialize(sv)          -- EnsureSchema + RebuildIndices
  IRY.Store:PrunePending()          -- pending старше pendingTtlDays
  IRY.Blacklist:Initialize()        -- кеш игнор-листа + события
  IRY.Icons:Initialize()            -- определение OSI и мост событий
  IRY:RegisterCommands()
  IRY.Observer:Initialize()         -- события игры
  IRY.Rename:Initialize()           -- события переименований
  IRY.Poller:Initialize()           -- таймер + события сброса
  IRY.TargetFrame:Initialize()      -- ZO_PostHook
  IRY.Chat:Initialize()             -- обёртки ссылок и kill feed
  IRY.Social:Initialize()           -- хуки друзей, гильдии и игнор-листа
  IRY.IconPicker:Initialize()       -- окно выбора иконки
  IRY.Browser:Initialize()          -- строки, регистрация top level
  IRY.Settings:Initialize()         -- панель LAM (может быть no-op)
  checkApiVersion()                 -- только предупреждение в чат
```

`IRY.sv` — таблица SavedVariables. Ничто не должно вызывать методы
`IRY.Store` до её инициализации: модули к этому моменту уже загружены, но лишь
*объявлены*.

## 4. Модель данных

```
IRememberYouSV
  schema          = 1
  nextId          = 1        -- не переиспользуется, пока есть данные
  nextPendingId   = 1
  players         = { [id] = Player }
  pending         = { Pending, ... }   -- массив, не словарь
  stats           = { created, linked, merged }
  settings        = { ...см. §11 }
```

```
Player
  id           number
  displayName  string       -- то, что видит пользователь
  isCustom     boolean      -- true, если имя задал пользователь
  createdAt    number       -- os.time(); задаёт порядок merge
  updatedAt    number       -- последнее касание; задаёт порядок списка
  notes        string
  aliases      { [accountKey] = Alias }
  characters   { [characterName] = Character }
  mergedInto   number?      -- надгробие: поглощён этим id
  mergedAt     number?
  mergeReason  string?      -- conflict | conflict-approved | friend-rename |
                            -- group-rename | manual
  icon         string?      -- один путь DDS, общий для всех поверхностей
  iconFrom     number?      -- происхождение при merge: чья иконка досталась
```

```
Alias
  firstSeen, lastSeen  number
  source               target | killfeed | guild | group | friend | manual
  confidence           confirmed | probable | manual

Character
  firstSeen, lastSeen  number
  classId, alliance, level, zoneId  number (0 = неизвестно)
  consoleId            string
```

Данные персонажа — это наблюдения, а не вечные факты: `Reconcile` заново
прикрепляет **известного** персонажа при каждом наблюдении, а `AttachCharacter`
перезаписывает только не-`nil`, непустые и не равные нулю значения. Так редкая
смена альянса или новый уровень попадают в базу без отдельного события, и так
же наблюдение без данных (kill feed, неполная строка гильдии) не стирает уже
известное. `0` означает «неизвестно», а не «без альянса».

### Ключи

* **Ключи аккаунтов хранятся без `@`.** `@Name` и `Name` нормализуются в `Name`,
  поэтому у одного человека один ключ независимо от того, какой API вернул
  строку. `Util.FormatAccount` возвращает `@` для показа.
* **Ключи персонажей хранятся как есть** (обрезанные пробелы, без разметки).
* В хранилище ключи регистрозависимы; без учёта регистра они сравниваются
  только там, где так делает игра (`Util.SameName`).

### Индексы

`account → id` и `character → id` живут только в памяти. Они **пересобираются
из `players`** после любого структурного изменения (`RebuildIndices`), а
сущности-надгробия пропускаются. Никогда не меняйте `aliases`/`characters`
напрямую без обновления индексов или пересборки.

## 5. Инварианты хранилища

Они несущие: нарушение проявляется как дубли сущностей или потерянные имена.

1. **Один ключ → одна сущность.** Аккаунт или персонаж принадлежит ровно одной
   не-надгробной сущности. `AttachAccount` / `AttachCharacter` не отбирают ключ
   у другого id и возвращают `false`; вызывающий должен вместо этого выполнить
   merge.
2. **`nextId` только растёт.** Id не переиспользуются, пока существует SV.
   Счётчики сбрасывает только `Wipe`, и он стирает всё.
3. **Надгробия постоянны.** `Merge` никогда не удаляет поглощённую сущность, а
   ставит `mergedInto`, `mergedAt`, `mergeReason`. Именно поэтому undo точный.
4. **Все id, попадающие в API, разрешаются** через `Store:ResolveFinal`, который
   идёт по цепочке `mergedInto` с защитой от циклов.
5. **`displayName` не пересчитывается при merge**, кроме случая, когда
   выжившая сущность не была пользовательской, а поглощённая была.
   `ResetDisplayName` пересчитывает имя из истории.
6. **Дефолты копируются, а не переиспользуются.** `ZO_SavedVars` может делать
   глубокую копию, но `IRY.BuildDefaults()` всегда отдаёт свежую таблицу
   `settings`. Никогда не передавайте сам `IRY.SettingsDefaults` туда, где
   пишут.

### Основные методы

| Метод | Возвращает / эффект |
| --- | --- |
| `Initialize(sv)` | починка схемы, индексы |
| `EnsureSchema()` | добивает недостающие поля верхнего уровня и ключи настроек из дефолтов (совместимость вперёд) |
| `Reconcile(account, character, source, info, confidence)` | общий upsert; возвращает `id, action, extra...`, где action — `created`, `linked`, `same`, `merged`, `invalid` |
| `AttachAccount` / `AttachCharacter` | `true`, если ключ добавлен этой сущности |
| `Touch` | обновляет `updatedAt` и `lastSeen` у известных ключей |
| `Merge(srcId, dstId, reason)` | копирует аккаунты/персонажей/заметки, при необходимости сохраняет пользовательское имя, ставит надгробие `src`, пересобирает индексы |
| `UndoMerge(srcId)` | `srcId` должен быть id надгробия; удаляет из `dst` только те ключи, чей индекс всё ещё указывает на `dst` |
| `Forget(id)` | удаляет одну самостоятельную сущность и связанные с ней записи pending; отказывает надгробиям и сущностям, на которые указывают надгробия |
| `OrderForMerge(a, b)` | `keep, drop`: побеждает более старый `createdAt`, при равенстве — меньший id |
| `DefaultDisplayName(player)` | самый ранний аккаунт по `firstSeen`, иначе самый ранний персонаж, иначе `?` |
| `SetDisplayName` / `ResetDisplayName` | пользовательское имя; очистка, максимум 32 байта, безопасно для UTF-8 |
| `List(limit)` | сущности без надгробий, сначала самые свежие по `updatedAt` |
| `Dump(id)` | массив отладочных строк |
| `AddPending` / `GetPending` / `FindBridgePending` / `RemovePending` / `PrunePending` | очередь ожидающих |
| `Purge(days)` | удаляет только не-пользовательские и не-надгробные сущности, у которых **самый свежий** `lastSeen` старше отсечки; `days <= 0` — ничего не делает |
| `Wipe()` | стирает игроков, pending, счётчики, статистику; настройки выживают |

В `Reconcile` есть собственная ветка конфликта (merge, когда один персонаж
указывает на два аккаунта). В обычной игре `Observer:Observe` перехватывает
этот случай раньше, так что ветка — запасная защита; при правках держите обе
одинаковыми.

## 6. Конвейер наблюдения

Любая запись проходит через одни ворота:

```
Observer:Observe(account, character, source, info, opts)
```

Входные данные должны быть уже нормализованы (`Util.NormalizeAccount`,
`Util.NormalizeCharacter`). Опции:

* `create` — можно ли создавать новую сущность (по умолчанию `true`),
* `quiet` — подавить уведомление в чат,
* `confidence` — переопределить уверенность, подразумеваемую источником.

### Уверенность

| Источник | Уверенность | Может создавать? |
| --- | --- | --- |
| `friend` | confirmed | да, включая оффлайн (последний известный персонаж) |
| `group` | confirmed | да |
| `target` (прицел) | probable | да |
| `killfeed` | probable | да (см. примечание) |
| `guild` | probable | **нет** — `create = false` |
| `manual` | manual | только при явном вызове API |

Примечание: `ui/chat.lua` вызывает `Observe` без флага `create`, поэтому kill
feed может создавать сущности, когда оба имени новые.

### Порядок решений

```
оба имени отсутствуют                    -> nil, "invalid"
вы сами и ignoreSelf включён             -> nil, "self"
нет совпадения ни по аккаунту, ни по персонажу
    и create == false                    -> nil, "unknown"
аккаунт -> A, персонаж -> B, A ~= B (конфликт)
    autoMergeOnConflict выключен         -> в очередь conflict pending, nil, "pending"
    иначе                                -> merge старого в выжившего, уведомление, "merged"
аккаунт неизвестен, персонаж -> B, уверенность probable
    и autoAcceptProbable выключен        -> в очередь bridge pending, nil, "pending"
    иначе                                -> обычный reconcile
обычный reconcile                        -> created | linked | same
    (добавлен аккаунт)                   -> уведомление о смене аккаунта
```

**Bridge pending** — это случай «вероятного переименования»: новый `@account`,
увиденный вместе с уже известным персонажем. Пара пришла от клиента и
заслуживает доверия; вывод «это тот же человек» — нет, поэтому он ждёт
пользователя.

`Observer:IsSelf` сравнивает нормализованные ключи с
`GetUnitDisplayName("player")` / `GetUnitName("player")`. При включённом
`ignoreSelf` (по умолчанию) проверка срабатывает до любого поиска в индексах.
Это не косметика: `EVENT_UNIT_CHARACTER_NAME_CHANGED` приходит и для юнита
`player` при смене локации и перезагрузке, а kill feed сообщает о ваших
собственных убийствах и смертях. Дополнительно `track/rename.lua` игнорирует
теги, которые не являются `reticleover` или `groupN`.

Снимок друзей создаёт сущности для всех друзей из списка, онлайн и оффлайн.
Оффлайн-друг даёт последнего известного персонажа; если клиент не вернул данных
о персонаже, сущность создаётся только по аккаунту.

`Observer:ApplyPending` сливает конфликты (сначала пересортировав) или
проигрывает bridge через `Reconcile`; `RejectPending` просто удаляет запись.

### Снимки и события

| Триггер | Вызов | Примечание |
| --- | --- | --- |
| `EVENT_RETICLE_TARGET_CHANGED` | `SnapshotTarget` | основной источник |
| `EVENT_GROUP_MEMBER_JOINED` | `SnapshotGroup(quiet)` + цель | |
| `EVENT_GROUP_MEMBER_LEFT` | `SnapshotGroup(quiet)` | |
| `EVENT_FRIEND_ADDED` | `SnapshotFriends(quiet)` | |
| `EVENT_PLAYER_ACTIVATED` | группа + друзья + обход гильдий | раз за вход/загрузку зоны |
| `EVENT_GUILD_DATA_LOADED` | `StartGuildScan` | состав подгружается лениво |
| `EVENT_GUILD_MEMBER_CHARACTER_UPDATED` | `GuildMember` | одна строка |
| тик поллера | `KeepUnit("reticleover", target)` | только при смене имён |

Обход гильдий идёт порциями (`GUILD_SCAN_CHUNK = 100` участников за шаг,
`GUILD_SCAN_DELAY = 100 мс`), чтобы не давать скачок кадра на больших аккаунтах.

`Observer.unitAccounts[unitTag]` помнит последний аккаунт, увиденный на юните
группы; это мост, который делает `EVENT_GROUP_MEMBER_ACCOUNT_NAME_UPDATED`
пригодным к использованию.

### Мосты переименований (`track/rename.lua`)

1. **Смена аккаунта у друга** — `OnFriendRenamed(old, new)`: merge, если
   существуют оба id, иначе новый алиас прикрепляется к старому id (confirmed).
   Если известен только новый id, старый алиас сохраняется для истории.
2. **Смена аккаунта в группе** — `OnGroupAccountUpdated(unitTag, accountName)`:
   терпим к порядку аргументов; сливает два известных id или прикрепляет новый
   алиас к id предыдущего аккаунта.
3. **Друг вошёл / сменил персонажа** — `OnFriendCharacterUpdated` добавляет
   персонажа к известному аккаунту (`create = false`).
4. **Переименование персонажа** — `OnUnitCharacterRenamed` заново снимает
   юнит с confirmed-уверенностью, и у сущности появляется ещё один алиас
   персонажа.

### Опрос цели (`track/poller.lua`)

Клиент шлёт `EVENT_RETICLE_TARGET_CHANGED` при смене объекта цели, но не когда
та же цель тихо меняет `@account`. Поллер перечитывает `reticleover` каждые
`pollIntervalMs` (минимум 250 мс) и вызывает `KeepUnit`, только если
нормализованная пара аккаунт/персонаж отличается от прошлой. Работает, когда
включены и `pollTarget`, и `captureTarget`; смена любой из этих настроек
вызывает `Poller:Apply()` из панели.

## 7. Поверхности отображения

### 7.1 Рамка цели (`ui/targetframe.lua`)

* Затрагиваются только `reticleover` и `reticleovertarget`.
* `ZO_PostHook(ZO_UnitFrameObject, "UpdateName")` и `"UpdateCaption"`.
* `ApplyName`: при `replaceTargetName` юнит ищется через `Resolver:ForUnit`,
  затем текст собирается заново: стабильное имя + значок сложности
  (`GetUnitOverlandDifficulty`, `ZO_CHALLENGE_DIFFICULTY_ICONS_GAMEPAD`) +
  маркер цели (`GetUnitTargetMarkerType`, `ZO_GetPlatformTargetMarkerIcon`).
* `ApplyCaption`: `hideTargetCaption` скрывает и очищает подпись;
  `replaceTargetCaption` собирает её как имя персонажа + титул.
* Тела хуков выполняются в `pcall`; ошибка сообщается только через `IRY:Debug`.
* `Refresh()` вызывает `ZO_UnitFrames_UpdateWindow` для двух тегов прицела;
  используется после переименования/merge/undo, чтобы изменение было видно без
  повторного наведения.

### 7.2 Ссылки в чате (`ui/chat.lua`)

`ZO_LinkHandler_CreatePlayerLink` один раз заменяется обёрткой. Суффикс
`" (Имя)"` вставляется **внутрь** `|h...|h`; полезная нагрузка ссылки не
трогается, поэтому клик по-прежнему ведёт на настоящий аккаунт.

`Chat:Suffix(account, character, shownName)` возвращает `nil`, если:

* `annotateChat` выключен;
* сущность неизвестна;
* стабильное имя совпадает с показанным (добавлять нечего);
* `annotateSelf` выключен, а имя принадлежит самому игроку.

Оба суффикса (`Chat:Suffix` и `Chat:SocialSuffix`) собирает один общий помощник
`buildSuffix`, чтобы правила «неизвестно / то же имя / это вы» не разъезжались.
Различаются они только настройкой, которая их включает (`annotateChat` против
`annotateSocial`).

Голое имя из ссылки считается декорированным `@account`, если клиент так
говорит, иначе — именем персонажа.

### 7.3 Kill feed (`ui/chat.lua`)

`CHAT_ROUTER:GetRegisteredMessageFormatters()[EVENT_PVP_KILL_FEED_DEATH]`
оборачивается один раз. Обёртка:

1. вызывает оригинальный форматтер;
2. отдаёт обоих участников в `Observer:Observe` (источник данных независимо от
   того, показывается строка или нет);
3. при `annotateKillFeed` вставляет суффикс после цветных имён убийцы и жертвы
   и в `message`, и в `narration`.

Переустановка повторяется на `EVENT_PLAYER_ACTIVATED`, потому что чатовый
роутер может закончить регистрацию форматтеров после загрузки аддонов, а другой
аддон может заменить запись (`pChat` — обычный подозреваемый).

### 7.4 Друзья, состав гильдии и игнор-лист (`ui/social.lua`)

Эти строки рисует сама игра, поэтому здесь только отображение. Три
`ZO_PostHook` — на `FRIENDS_LIST_MANAGER:SetupEntry`,
`GUILD_ROSTER_MANAGER:SetupEntry` и `IGNORE_LIST_MANAGER:SetupEntry` —
дописывают ` |c8F8F8F (Имя)|r` к лейблу `DisplayName`. Настоящее имя аккаунта
остаётся спереди и в ключе сортировки; ничего не заменяется. В игнор-листе
хранится только имя персонажа: ручная иконка ищется по персонажу, и у него же
спрашивают чёрный список.

* Тело хука читает только что установленный текст и дописывает один раз.
  `SetupEntry` перезаписывает лейбл при каждом обновлении, поэтому сбрасывать
  ничего не нужно; цветной маркер защищает от двойной установки.
* Ничего не меняет размеры. В обоих списках лейбл `Zone` привязан к правому краю
  `DisplayName`, поэтому расширение имени сдвигало колонку «Локация» вправо, а
  последующее сужение `Zone` обрезало текст локации — из-за этого колонки и
  «плыли» от строки к строке. `AppendSuffix` вместо этого сравнивает
  `DisplayName:GetTextWidth()` с собственной шириной лейбла. Если суффикс
  `" (Имя)"` помещается — он дописывается целиком; если нет, сокращается только
  запомненное имя, по одной букве (`utf8Prefix` никогда не рвёт символ UTF-8),
  пока не поместится `" (Имя...)"`. Если свободного места меньше ~60 px, суффикс
  не показывается вовсе — одна буква смысла не несёт.
* `GetTextWidth` используется только для измерения; если метода нет, суффикс
  дописывается как есть, и многоточие ставит сама игра.
* Только клавиатурный интерфейс: при `IsInGamepadPreferredMode()` разметка
  консоли пропускается.
* Хуки ставятся один раз и перепроверяются на `EVENT_PLAYER_ACTIVATED`, чтобы
  поздняя замена другим аддоном тоже была покрыта.
* Суффикс берётся из `Chat:SocialSuffix` (под управлением `annotateSocial`), а
  не из второй реализации.
* Иконка — это inline-префикс `|t<размер>:<размер>:<путь>|t ` в том же лейбле.
  `plain()` и `splitIcon()` вырезают его перед измерением, поэтому логика ширины
  не меняется, а префикс переписывается на месте, а не добавляется второй раз.
  `AppendSuffix` явно резервирует его ширину.
* OdySupportIcons умеет рисовать ту же иконку в своём оверлее `StatusIcon`.
  Когда `Icons:OsiHandles2D(surface, displayName)` говорит, что OSI уже рисует
  иконку именно этого человека (опция OSI включена **и** аккаунт есть в нашем
  pushed-словаре), строка пропускает только inline-иконку — суффикс запомненного
  имени всё равно дописывается. Проверка по личности, а не по поверхности:
  у друзей вне группы ничего не запушено, и они сохраняют свою иконку.

### 7.5 Вывод (`core/print.lua`)

* `IRY:Print` — системная строка с префиксом.
* `IRY:Debug` — серая, только при `settings.debug`.
* `IRY:NotifyAccountLinked` — строка «смена ID», фильтруется по `notifyLevel`
  (`off` / `confirmed` / `all`).
* `IRY:NotifyMerged` — строка автоматического merge; намеренно использует
  «сырые» имена сущностей, потому что поглощённое имя нужно показать таким,
  каким оно было *до* слияния.
* `IRY:NotifyPending` — одна строка с id и подсказками `/pa yes|no`.
* `IRY:RefreshUI` — единственная точка «перерисовать всё».
* `IRY:PurgeOldPlayers(days)` — общая для кнопки настроек, браузера и
  `/pa purge`; печатает результат и возвращает число удалённых.

### 7.6 Иконки игроков (`core/icons.lua`, `core/blacklist.lua`, `core/iconpacks.lua`)

Все поверхности спрашивают иконку в одном месте — `IRY.Icons`, — и ни одна не
решает сама. Поэтому у игрока одна и та же иконка везде.

**Порядок** (`Icons:Resolve`): `showIcons` выключен → ничего; ручной `player.icon`
→ этот путь; `blacklistIcons` включён и персонаж игнорируется → метка чёрного
списка; иначе ничего. `ForUnit` отдаёт чёрному списку **имя персонажа**
(`GetUnitName`), а ручную иконку ищет по id сущности. `GetUnitDisplayName` — это
`@account`, с игнор-листом он не совпадёт никогда.

**Библиотека.** ESO не умеет перечислять файлы, поэтому `core/iconpacks.lua` —
рукописный манифест `{ { id, title, icons = { path, ... } }, ... }`. `AllPaths`
разворачивает и дедублирует его и отбрасывает всё, что не проходит
`IRY.IsIconPath` (`IRememberYou/icons/<pack>/<name>.dds`, нижний регистр, без
пробелов). Плохой путь игра молча не нарисует, отсюда проверка. Своя библиотека
намеренно: папка OSI не входит в наш релиз и может переехать.

**Назначение.** Единственная точка записи — `player.icon`; `Store:SetIcon` и
`Store:ClearIcon` проверяют путь и сбрасывают `iconFrom`. При merge получатель
наследует `src.icon` с `dst.iconFrom = srcId`, поэтому undo проходит всю цепочку
и снимает иконку у всех, кто получил её так. Панель подробностей и `/pa icon`
зовут `Icons:Assign/Clear`, а те заканчиваются `IRY:RefreshUI()`.

**2D-поверхности.** Рамка цели и список в браузере используют одну и ту же
inline-разметку `|t<размер>:<размер>:<путь>|t `; социальные строки тоже (см.
7.4). Размер берётся из `settings.iconSize2d` и зажимается в
`IRY.ICON.min`/`max` (для социальных строк — в `socialMax`, для строк браузера —
в 24 px, чтобы строка высотой 26 px не росла).

У рамки цели два режима. Когда имя пересобирается, иконка входит в собранную
строку. Когда нет (`replaceTargetName` выключен или игрок ещё не известен базе —
игнорируемый незнакомец тоже должен получить метку), иконка дописывается перед
текстом самой игры, а точный префикс запоминается на лейбле, чтобы его можно
было снять, не угадывая, какие inline-текстуры поставила игра.

**Чёрный список.** `core/blacklist.lua` держит в памяти словарь имён персонажей в
нижнем регистре, собранный из `GetNumIgnored`/`GetIgnoredInfo`; в SavedVariables
он не попадает. Порядок аргументов `GetIgnoredInfo` отличается между уровнями
API, поэтому имя берётся как первая непустая строка из возвращённых значений.
Проверка одного имени предпочитает штатный `IsIgnored(name)`, если он есть, и
падает обратно на словарь. Словарь перестраивается на `EVENT_IGNORE_ADDED`,
`EVENT_IGNORE_REMOVED`, `EVENT_IGNORE_NOTE_UPDATED` и `EVENT_PLAYER_ACTIVATED`;
константы событий, которых нет в клиенте, пропускаются, а не ломают
`Initialize`. Путь метки — `settings.blacklistIcon` или, пока он nil, встроенная
`IRY.ICON.blacklistDefault` (`rooster.dds`); если её нет в манифесте, берётся
первая иконка первого пака.

**3D через OdySupportIcons (опционально).** `_G.OSI` на нашей загрузке обычно
nil (OSI сортируется позже), поэтому `Icons:Initialize` ждёт
`EVENT_ADD_ON_LOADED` с `addOnName == "OdySupportIcons"`, откладывает
`zo_callLater(…, 0)`, чтобы OSI успел инициализироваться и восстановить кеш, и
только потом применяет. Все вызовы OSI защищены и обёрнуты в `pcall`.

* Участники группы: для каждого `groupN` иконка пушится через
  `OSI.SetCustomIconForUnit(lower(displayName), path, {1,1,1})`. OSI хранит
  `special` по имени в нижнем регистре **ровно в том виде, в каком его вернула
  игра** (`@account` на ПК); наш ключ учёта снимает `@`, чтобы узнавать того же
  человека в 2D-строках.
* Перед пушем снимаются `OSI.special[raw]` и запись кеша OSI. Если `save`
  включён, `SetCustomIconForUnit` записывает нашу временную иконку в
  SavedVariables OSI; `UpdateCache(raw, saved)` сразу возвращает старое значение.
  Снятие восстанавливает прежний special (или кеш) и затем кеш.
* Цель под прицелом не может использовать `special` (только группа), поэтому это
  одна `OSI.CreatePositionIcon`, чей callback читает
  `GetUnitRawWorldPosition("reticleover")` **внутри цикла обновления OSI** и
  двигает `icon.x/y/z`. Текстура, размер и offset живут в `icon.data`; смена
  текстуры пишется туда и в контрол через `UpdateIconData`.
  `DiscardPositionIcon` вызывается, когда цель перестаёт быть игроком или наша
  иконка исчезает, иначе слот останется висеть.
* `Icons:Apply` идемпотентен: он зовёт OSI только если путь изменился или в
  special уже не наша текстура. Он же снимает ключи, которых больше нет в
  группе, — ушедший или переименованный участник не оставит иконку.
* `showIcons == false` вызывает `RemoveAll`: все пуши восстанавливаются, а
  позиционная иконка отбрасывается. То же происходит на `EVENT_IGNORE_*` через
  `IRY:RefreshUI()` и при входе — отложенным `Apply` после обработчика
  `EVENT_PLAYER_ACTIVATED` самого OSI.
* События: вход/выход/подключение/отключение участника,
  `EVENT_GROUP_MEMBER_ACCOUNT_NAME_UPDATED`, `EVENT_UNIT_CHARACTER_NAME_CHANGED`
  (только `groupN` и `reticleover`), `EVENT_RETICLE_TARGET_CHANGED`,
  `EVENT_RETICLE_TARGET_PLAYER_CHANGED`, два события игнор-листа,
  `EVENT_ADD_ON_LOADED`, `EVENT_PLAYER_ACTIVATED`.
* Без OSI 2D-поверхности работают как обычно; `Icons:OsiStatus()` возвращает
  `ready`, `custom-off` (в OSI выключены свои 3D-иконки) или `missing`.

## 8. Окно списка игроков

`ZO_ScrollList` не используется: фиксированный пул из **40** строк-кнопок
(`MAX_ROWS`), заполняемый из постраничного снимка. Так окно дешевле и не зависит
от изменений API скролл-списков. Заполняются и показываются только те строки,
что помещаются в текущую высоту.

### Разметка

`ui/browser.xml` объявляет `IRY_Browser` — растягиваемый `TopLevelControl`
(`movable`, `clampedToScreen`, `mouseEnabled`, `resizeHandleSize="16"`) — и два
виртуальных шаблона: `IRY_BrowserRow` (лейблы `Id`, `Name`, `Meta`, `Seen` и
скрытая подсветка `Highlight`) и `IRY_DetailLine` (`Name`, `Meta`).

Размер по умолчанию — **660 × 680**; ограничения — минимум **660 × 420**,
максимум **1600 × 1200**. Строки привязаны `TOPLEFT 124` / `BOTTOMRIGHT -112`,
поэтому растягиваются вместе с окном. Футер — контрол высотой 96 px, привязанный
к нижнему краю; его дети используют собственные смещения от своего левого
верхнего угла.

Группы контролов:

* шапка: `Title`, `Close`, `SearchBGEdit`, `TabPlayers`, `TabPending`, `Count`,
  `HeadId/Name/Meta/Seen`;
* список: `Rows` и 40 сгенерированных `IRY_BrowserRowN`;
* футер: сводка `Detail`, `RenameBGEdit`, `Rename`, `Reset`, `Merge`, `Undo`,
  `Yes`, `No`, `Prev`, `PageLabel`, `Purge`, `Next`;
* панель подробностей: `IRY_BrowserDetailPanel` с `…Title`, `…Lines` (внутри —
  сгенерированные `IRY_DetailLineN`), `…Hint`, `…Close`, `…BG`.

У кнопок футера и детей панели подробностей явные глобальные имена вместо
`$(parent)…`. Скрипт проверки размеров страницы из чек-листа релиза считает, что
`$(parent)` — это окно, а панель подробностей им не является.

### Состояние

```lua
state = {
  tab, page, search, selected, mergeFirst, data,
  left, top, width, height, rowsPerPage,
  detailOpen, detailPlayerId, detailOffset, detailVisible, detailItems,
}
```

* `data` — плоский массив `{ kind = "player", player = ... }` или
  `{ kind = "pending", entry = ... }`, пересобирается при каждом `Refresh`.
* `Collect` фильтрует по подстроке в нижнем регистре: отображаемое имя, все
  ключи аккаунтов, все персонажи. Ведущий `@` в запросе отбрасывается, потому
  что аккаунты хранятся без него. Игроки идут в порядке `Store:List` (свежие
  первыми); ожидающие — по id.
* `selected` — id игрока на вкладке игроков и id ожидающего на вкладке
  ожидающих. Счётчики независимы — никогда не ищите pending id как игрока.
* `mergeFirst` хранит первый id при объединении в два клика.
* `rowsPerPage` вычисляется, а не настраивается: `UpdatePageSize` делит
  `IRY_BrowserRows:GetHeight()` на `ROW_HEIGHT` (26) и ограничивает результат
  5..`MAX_ROWS`. Если контрол ещё не разложен, берётся высота окна минус
  фиксированные смещения.

### Поведение

* Строки создаются в `Initialize` через `CreateControlFromVirtual` и получают
  `row.index` (1..`MAX_ROWS`); обработчик клика отображает его в
  `data[(page-1)*rowsPerPage + index]`.
* `Refresh` сначала пересчитывает размер страницы, поэтому изменение размера
  окна сразу меняет число видимых игроков и число страниц.
* Объединение в два клика: первый клик запоминает `mergeFirst`, второй сливает
  `OrderForMerge(first, selected)`. `UndoLastMerge` ищет надгробие с самым
  свежим `mergedAt`.
* Переименование фиксируется по Enter, по кнопке и по потере фокуса — но при
  потере фокуса только если текст реально изменился, чтобы клики вокруг не
  спамили чат.
* `Purge` вызывает `IRY:PurgeOldPlayers()` с сохранённым сроком хранения.
* Колесо мыши листает страницы (`TurnPage(-delta)`); кнопки Prev/Next делают то
  же.
* Геометрия сохраняется по `OnMoveStop` **и** `OnResizeStop` в
  `settings.browserLeft/browserTop/browserWidth/browserHeight` (намеренно не в
  дефолтах; `nil` означает «по центру, размер по умолчанию»). `Show`
  ограничивает сохранённый размер рамками и текущим размером экрана.

### Панель подробностей

Панель — **дочерний** контрол `IRY_Browser`, а не второе top-level окно. Одно
это решение даёт нужное поведение бесплатно:

* скрытие списка скрывает и панель;
* смена вкладки, закрытие окна, `Escape`, подтверждение/отклонение ожидающей
  записи и `/pa forget` вызывают `CloseDetail`;
* выбор другого игрока лишь заменяет содержимое (`OpenDetail` сбрасывает
  прокрутку), поэтому второй панели не бывает.

`PlaceDetailPanel` привязывает её справа от окна (`TOPLEFT`/`BOTTOMRIGHT`
относительно правого края окна) и переключается на левую сторону, если справа
она вышла бы за экран. После изменения размера панель ставится заново.

`BuildDetailItems` собирает плоский список, который рисуется в `MAX_DETAIL_LINES`
(40) шаблонных строк по 18 px:

```
header   Аккаунты
account  @Имя                          последний раз
blank
header   Персонажи
character Имя                          альянс · уровень
muted    аккаунты не записаны / персонажи не записаны
```

Текст альянса берётся из `Util.FormatAlliance` (`GetAllianceName` +
`ZO_CachedStrFormat(SI_ALLIANCE_NAME, …)`), поэтому следует языку клиента.
Прокрутка колесом: `ScrollDetail` ограничивает смещение диапазоном
`#items - visible`.

### Интеграция со сценами

`Initialize` регистрирует окно через
`SCENE_MANAGER:RegisterTopLevel(window, false)`. Затем `Show`/`Hide` идут через
`ShowTopLevel`/`HideTopLevel`, что поддерживает корректным счётчик
`numTopLevelShown` менеджера сцен и делает так, что первый `Escape` закрывает
окно, а не открывает игровое меню. Если API недоступен, используется fallback на
`SetHidden`. Не обходите эти вызовы «сырым» `SetHidden(false/true)`, когда
`usesTopLevel` истинно.

`SetDimensionConstraints` применяется в `Initialize`, если доступен; без него
окно всё равно растягивается, просто без игровых ограничений — `Show` сам
ограничивает сохранённый размер.

После показа `Show` вызывает `IRY_Browser:BringWindowToTop()` (под проверкой на
`nil`). ESO укладывает видимые top-level окна в порядке регистрации, поэтому
окно, открытое слэш-командой, иначе может оказаться под окном, зарегистрированным
позже, и выйдет наверх только по первому клику мышью.

## 9. Панель настроек

`ui/settings.lua` использует LibAddonMenu-2.0. `local LAM = LibAddonMenu2`
захватывается при загрузке файла; с `OptionalDependsOn` это безопасно. Без LAM
`Settings:Initialize` возвращает `false`, и больше ничего не меняется — аддон
полностью работоспособен через команды и клавишу.

* Id панели: `IRememberYouOptions`; слэш-команда: `/iryoptions`.
* Включены `registerForRefresh` и `registerForDefaults`, поэтому панель
  перечитывает значения, а кнопка «Defaults» сбрасывает к
  `IRY.SettingsDefaults` (через те же сеттеры, то есть побочные эффекты
  срабатывают).
* Геттеры читают `sv.settings` при каждом вызове; сеттеры пишут прямо в неё.
* Побочные эффекты: чекбоксы рамки цели и иконок вызывают `IRY:RefreshUI()`;
  `captureTarget`, `pollTarget` и `pollIntervalMs` вызывают
  `IRY.Poller:Apply()`.

Секции: рамка цели, чат, сбор данных, связывание, иконки игроков,
обслуживание. Первый виджет — кнопка «Открыть список игроков»; из секции иконок
ещё открывается выбор иконки для игнор-листа.

## 10. Команды

`ui/commands.lua` регистрирует `/pa` и `/iry` в `SLASH_COMMANDS`. Разбор — простая
цепочка `if/elseif` по первому слову в нижнем регистре.

* `resolveId` принимает `#12`, `12`, `@Account`, `Account` или имя персонажа и
  ищет через `Resolver:ForName`.
* `resolveRawId` сначала пробует точный id игрока (нужно для надгробий, которых
  нет в индексе), затем откатывается к `resolveId`.
* `/pa purge [days]`: нечисловой аргумент печатает строку использования; `0` (или
  отсутствие аргумента при настройке 0) печатает «выключено»; удаляет только
  положительное число.
* `/pa forget <id>`: удаляет одну сущность. Отказывает надгробию и сущности, на
  которую указывают надгробия, чтобы цепочки undo оставались валидными; заодно
  убирает записи pending, ссылающиеся на удалённую сущность.
* `/pa yes|no [n]` по умолчанию берут первую ожидающую запись.
* `IRY.Commands.Handle` / `ResolveId` открыты, чтобы браузер и тесты
  использовали тот же разбор.

Отладочные подкоманды: `on|off`, `fake <acc> <char>`, `bridge <acc> <char>`,
`conflict`, `dump <id>`, `ignore`, `wipe confirm`. `fake` и `bridge` обе вызывают
`Observe` и различаются только текстом вывода; `conflict` симулирует случай
merge A/B → C/D → C/B; `ignore` печатает кеш игнор-листа; `wipe confirm` стирает
базу и сбрасывает id.

Команды иконок: `/pa icons [on|off]` переключает `showIcons` (без аргумента
печатает состояние, размер в UI, пометку игнорируемых и статус OSI);
`/pa icon <id> [путь|clear]` показывает, задаёт или снимает иконку игрока через
`Icons:ResolvePlayer`. Путь обязан проходить `IRY.IsIconPath`.

## 12. Локализация

* `lang/en.lua` всегда определяет `IRY.L`.
* `lang/ru.lua` заменяет `IRY.L`, когда `GetCVar("language.2") == "ru"`
  (обёрнуто в `pcall`, чтобы отсутствующий CVar не ломал загрузку).
* В обеих таблицах должны быть **ровно одинаковые ключи**. `HELP` — массив
  строк; число строк в обоих языках должно совпадать.
* Название клавиши — игровая строка, а не запись `IRY.L`:
  `ZO_CreateStringId("SI_BINDING_NAME_IRY_TOGGLE_BROWSER", ...)`. Английское
  значение создаётся в `lang/en.lua`; русский файл перекрывает его внутри
  проверки языка, поэтому меню «Управление» показывает язык клиента.
* Пользовательский текст никогда не живёт в логике Lua; команды, настройки,
  заголовки строк и сообщения идут через `IRY.L`.
* Файлы — UTF-8 **без BOM** (парсер Lua в игре не любит BOM). Кириллические
  имена обрезаются по границе UTF-8 в `Util.SanitizeDisplayName`.

## 13. Соглашения и подводные камни

* Один глобал: `IRY`. Всё висит на нём; файлы не создают других глобальных
  имён (исключение — имена контролов XML с префиксом `IRY_Browser...`).
* Шапки файлов объясняют *почему*, а не *что*. Держите этот стиль.
* Любой новый хук в код игры идёт через `ZO_PostHook` или защищённую обёртку и
  устанавливается ровно один раз (сравнение с сохранённой обёрткой).
* Хуки и post-hook'и обёрнуты в `pcall` там, где ошибка могла бы сломать рамку
  цели.
* Нормализуйте имена до попадания в хранилище; хранилище ожидает канонические
  ключи.
* Разрешайте каждый id через `ResolveFinal` перед чтением полей.
* Не обращайтесь к методам `IRY.Store` при загрузке файлов: SV ещё не создан.
* Не добавляйте зависимость от LAM для основных функций.
* `ZO_SavedVars` делает глубокую копию дефолтов; и всё же не отдавайте одну
  таблицу настроек двум владельцам.
* Добавление строки на страницу больше не требует правки константы: размер
  страницы берётся из высоты окна. Не возвращайте фиксированный `PAGE_SIZE`.
  Если меняете `ROW_HEIGHT` в `ui/browser.lua`, синхронизируйте его с высотой
  шаблона строки в `ui/browser.xml`, а `ROWS_TOP_OFFSET` / `ROWS_BOTTOM_OFFSET` —
  с привязками `Rows`.

### Известные несоответствия

* `Store:Reconcile` дублирует конфликтный merge, который обычно выполняет
  `Observer:Observe` раньше. Оба пути должны вести себя одинаково.
* `/pa debug fake` и `/pa debug bridge` — функционально один и тот же вызов с
  разным текстом вывода.
* Шапка `ui/commands.lua` всё ещё упоминает «Phase 1»; интерфейс уже есть.

## 14. Ограничения

* Игрока можно узнать, только если клиент хотя бы раз показал аккаунт и
  персонажа вместе (цель, группа, друг, kill feed). Данные гильдии только
  обогащают известные аккаунты.
* Друзья берутся из списка друзей даже оффлайн, поэтому могут появиться с
  устаревшим последним персонажем.
* Вы сами не записываетесь, пока включён `ignoreSelf` (по умолчанию). Строку,
  созданную старой версией, нужно убрать через `/pa forget <id>`.
* Состав гильдии подгружается лениво; данные приходят через секунды после входа,
  порциями.
* Оформление имён на консолях/других платформах отличается; нормализация и
  `FormatAccount` покрывают обычные случаи, но это наименее проверенная область.
* Ожидающие записи чистятся только при входе (`pendingTtlDays`), не по таймеру.
* Импорта/экспорта и резервных копий нет; `IRememberYouSV` — единственная
  копия.
* Иконкам нужен непустой манифест `core/iconpacks.lua`; без поставленных DDS
  ничего не рисуется. 3D-иконки вдобавок требуют OdySupportIcons с включённой
  опцией «показывать свои 3D-иконки». Собственные оверлеи OSI (уникальные и
  LibCustomIcons) от нашего правила не зависят и могут появиться рядом с нашей
  иконкой в 2D-списке.

## 15. Чек-лист тестирования

Перед релизом, в живом клиенте:

1. `/reloadui` на свежем персонаже: ошибок Lua нет, строка загрузки и версия
   верные.
2. Навести на игрока: имя и подпись заменены; значок сложности и маркер цели на
   месте; рамки группы не тронуты.
3. Переименование через `/pa rename <id> <имя>` и через браузер (Enter, кнопка,
   потеря фокуса); `/pa reset <id>` возвращает первый аккаунт.
4. Смена аккаунта: `/pa debug bridge <newAcc> <knownChar>` → запись в pending,
   одна строка в чате, `/pa yes` применяет, `/pa no` отбрасывает.
5. Конфликт: `/pa debug conflict` → автоматический merge (по умолчанию) и при
   выключенном `autoMergeOnConflict` → conflict pending.
6. `/pa undo <id>` точно восстанавливает обе сущности (аккаунты и персонажи).
7. Браузер: поиск с `@` и без, обе вкладки, страницы и колесо мыши, объединение
   двух строк, отмена последнего merge, purge при 0 и при положительном
   значении, подсветка при наведении, `Escape` закрывает и не открывает игровое
   меню.
8. Размер браузера: потянуть за правый нижний угол, проверить ограничения
   min/max, что число видимых строк меняется сразу и что размер с позицией
   переживают `/reloadui`. Уменьшить окно до нескольких строк.
9. Панель подробностей: щёлкнуть по игроку, проверить все аккаунты и персонажей
   с альянсом и уровнем; щёлкнуть по другому игроку — та же панель меняет
   содержимое; сменить вкладку, закрыть список и нажать `Escape` — она исчезает;
   открыть её, когда окно стоит у правого края экрана — она переезжает влево;
   прокрутить колесом до последней позиции в подсказке.
10. Панель настроек: каждый контрол сразу меняет поведение; «Defaults»
    возвращает значения, и побочные эффекты (перезапуск поллера) срабатывают.
11. Русский клиент: все строки, ширина кнопок, название клавиши; ничего не
    вылезает.
12. Без LibAddonMenu: аддон загружается, панели нет, команды и клавиша работают.
13. С `pChat` (если есть): пометки в kill feed и ссылки по-прежнему рисуются.
14. Суффикс в чате: не применяется к себе, не дублируется, когда стабильное имя
    совпадает с показанным.
15. Себя: сменить локацию, перезагрузиться, войти в группу — вы не должны
    появляться в списке. Выключить `ignoreSelf` и убедиться, что наблюдение
    снова может вас создать; включить обратно.
16. `/pa forget <id>` удаляет самостоятельную строку; отказывает надгробию и
    сущности с влитыми игроками, с понятным сообщением.
17. Оффлайн-друг: при друге оффлайн `/reloadui` должен создать строку с его
    последним известным персонажем (или только аккаунтом, если персонаж
    неизвестен).
18. Друзья и состав гильдии: запомненное имя дописывается серым, имя аккаунта не
    меняется и по-прежнему стоит первым в сортировке; колонка «Локация»
    начинается на одном и том же x в каждой строке — с запомненным именем и без
    него, — и текст локации нигде не обрезан; длинное запомненное имя сокращается
    многоточием, а не уезжает в следующую колонку; выключение `annotateSocial`
    убирает суффикс при следующем обновлении; многократно обновляемая строка не
    получает второй суффикс.
19. Альянс: навести на игрока, запомнить альянс в панели подробностей, затем
    встретить его в другом альянсе (гость кампании, группа) — значение
    обновится при следующем наблюдении и не сбросится в «неизвестно» после
    строки kill feed без данных.
20. Иконки, 2D: задать иконку в панели подробностей; она появляется в рамке
    цели, у друзей, в гильдии, игнор-листе и строке браузера для этого человека;
    источник подписан «вручную». Снять — картинка исчезает везде.
21. Иконки, игнор-лист: добавить персонажа в игнор; метка появляется на всех
    поверхностях после события игнор-листа; ручная иконка у того же человека
    важнее. Выключить `blacklistIcons` и `/pa icons off` — всё скрывается и
    возвращается.
22. Иконки, 3D: с загруженным OdySupportIcons у участника группы появляется
    иконка над головой, у цели под прицелом — тоже; сначала задать участнику
    свою иконку в OSI и убедиться, что она вернулась после снятия нашей. Выйти
    из группы — ничего не остаётся висеть. Без OSI 2D-поверхности работают, а
    `/pa icons` пишет «не загружен».

Пункты, ещё не проверенные в живом клиенте (первые подозреваемые, если что-то
выглядит не так): `GetAPIVersion()` против `101050 101051` в манифесте, порядок
аргументов события смены аккаунта в группе, события переименования оффлайн-друга,
тайминг состава гильдии, kill feed при выключенной настройке интерфейса,
совместимость с `pChat`, ширина русских подписей, `Label:GetTextWidth()` на
шаблонах строк соцсписков (на нём держится подгонка суффикса), ручка изменения
размера при разных масштабах интерфейса, привязка панели подробностей у краёв
экрана, порядок
аргументов `SetupEntry` у `FRIENDS_LIST_MANAGER` / `GUILD_ROSTER_MANAGER`,
локализованные названия альянсов и то, что `BringWindowToTop` действительно
поднимает список (это метод контрола на стороне C, статически его не проверить).
Также не проверены: форма ключей `OSI.special` на консолях,
`GetUnitRawWorldPosition("reticleover")` для любого игрока под прицелом, точное
восстановление кеша OSI и то, что `GetIgnoredInfo` возвращает имя персонажа на
всех языках клиента.

## 16. Чек-лист релиза

Версия живёт в `IRememberYou.txt` (`## Version:`). Workflow её только читает и
ничего не пишет; `IRY.version` в `core/constants.lua` и `## AddOnVersion:`
должны с ней совпадать, иначе CI падает.

1. Поднять `## Version:` и `## AddOnVersion:` (`major*10000 + minor*100 + patch`;
   `0.3.0` даёт `300`) в `IRememberYou.txt` и `IRY.version` в
   `core/constants.lua`.
2. Добавить или обновить раздел `## [<version>]` в `CHANGELOG.md`.
3. Закоммитить и запушить в `main`.
4. Workflow упакует аддон, создаст тег `v<version>` и опубликует GitHub-релиз
   с `IRememberYou_v<version>.zip` и двуязычной инструкцией по установке.
   Для версии, у которой релиз уже есть, ничего не делается — чтобы выпустить
   снова, подними версию.
5. Пуш тега вручную тоже работает, но тег должен быть ровно `v<version>`;
   обычный путь — пуш в `main`.
6. Прогнать живой чек-лист выше (§15) по архиву до анонса релиза.
7. Загрузить тот же архив на ESOUI вручную — публичного API загрузки у сайта
   нет.

Архив собирается из рабочей копии, из него исключены `.git`, `.github`,
`.gitignore`, `.gitattributes`, `DEVELOPMENT.md` и `DEVELOPMENT.ru.md`; на корне
лежит `IRememberYou/IRememberYou.txt`. Workflow падает, если в архиве остался
хоть один скрытый файл или файл `DEVELOPMENT*`, поэтому документация для
разработчиков в релиз случайно не попадёт.

Чтобы перевыпустить ту же версию (например, после исправления содержимого
архива), удалите релиз и тег `v<version>` на GitHub и снова запушьте `main`:
релиз создастся заново с текущего коммита.

Статические проверки больше не входят в workflow, потому что CI ничего не
устанавливает. Прогонять их руками, если изменение рискованное: `luac -p` из
`Input/lua-5.1.5_Win64_bin/`, разбор обоих XML через `[xml]` и сравнение
ключей `IRY.L` в `lang/en.lua` и `lang/ru.lua`.

## 17. Рецепты

**Добавить источник данных**

1. Добавить `IRY.SOURCE.X` и его приоритет в `core/constants.lua`.
2. Вызвать `IRY.Observer:Observe(account, character, IRY.SOURCE.X, info, opts)`
   с нормализованными ключами. Явно решить про `create`, `quiet` и
   `confidence`.
3. Если нужен переключатель — добавить дефолт в `SettingsDefaults`, чекбокс
   LAM и строки в оба языка.
4. Описать уровень доверия в шапке `observer.lua`.

**Добавить настройку**

1. Добавить ключ и дефолт в `IRY.SettingsDefaults`.
2. Добавить контрол в `ui/settings.lua`; подключить побочный эффект, если
   значение читается при старте (поллер, хуки, разметка).
3. Добавить строки `OPT_*` в оба языковых файла.
4. Упомянуть в обоих README, если настройка видна пользователю.

**Добавить команду**

1. Добавить ветку в `handle` в `ui/commands.lua`.
2. Добавить строку использования в `HELP` на обоих языках.
3. Вынести логику в метод, если её должен переиспользовать браузер.
4. Обновить таблицу команд в обоих README.

**Добавить строку**

1. Добавить её в `lang/en.lua` и `lang/ru.lua` с одинаковым ключом.
2. Использовать `IRY.L.KEY` в месте вызова; никогда не встраивать текст в код.

## 18. Потенциальные задачи

Это ещё не баги, а идеи и шероховатости, записанные, чтобы не потерялись.

* **Растягивание окна по диагонали.** Потянув за угол, окно сейчас меняет
  размер только по одной оси; движение мыши одновременно по `dx` и `dy` не
  растягивает обе стороны. Подозрения: ручка изменения размера (16 px у
  `IRY_Browser`) частично перекрыта футером (привязан `BOTTOMRIGHT -8,-8`,
  высота 96 px) или кнопкой `Next` в его правом верхнем углу, поэтому курсор
  выходит за ручку в начале перетаскивания; либо ручка отслеживает только одну
  ось, когда курсор покидает квадрат 16 px. Проверить: увеличить
  `resizeHandleSize`, поднять футер на несколько пикселей, посмотреть при 100 % и
  при масштабированном интерфейсе, с открытой и закрытой панелью подробностей.
* **Вывод окна на передний план при открытии** исправлен через
  `BringWindowToTop`; если сломается снова — проверить, что вызов по-прежнему
  идёт до первого обновления.
